## 0. 结论摘要

1. **数据整体合理、内部自洽**：32 个有效点（4MB 16 + 8MB 16）全部满足
   keys/s × 对象大小 = 吞吐、queries/s × batch = keys/s、Little's law 误差 < 0.25%。
2. **直写路径已到 PCIe 3.0 x16 HBM write 上界**：a/c 在 16/16 达到 12.69 / 12.68 GiB/s，
   即 PCIe 3.0 x16 的 **86.5%**；UB 裸单请求 86.4 µs = 45.1 GiB/s（E3-U），
   b 的 180 µs 是 Mooncake UB 栈（+94 µs），不是链路上限（E3-I / E3-L2 / E3-U）。
3. **暂存路径的差值就是 host 暂存 + memcpy**：b/d 吞吐为直写的 61%–82%，
   8MB 下因大对象摊薄固定开销而提升（b 8.62→9.43，d 9.40→10.37 GiB/s）。
4. **8MB b 16/16 的唯一异常已定位并修复**：UB transport staging pool 默认 1 GiB，
   小于 2 GiB 在飞；设 4 GiB（4294967296）后 9.43 GiB/s / 211.6 ms，A/B 对照确认。
   **E3-V 复核：4MB/8MB 的 16/16（batch=16）两个池都在用（client + UB staging）；
   E3-G 的 4G 修复根因就是 UB staging 池，方向正确；1/1 只用 client 池（§3.9.3）。**
5. **最终两表 16/16 格全部有效**。剩余风险（node2 load 尖峰、1/16 与 16/16 仅 2 轮、
   b 路径计数器为 0、8MB verify 互斥）已在交付说明中注明，不改变结论。
6. **E3-U/E3-N 定量并验证了 b 的剩余空间**：裸 UB 单请求 86.4 µs（45.1 GiB/s），Mooncake b
   的 180 µs 是栈开销（+94）；PCIe 266 µs 是线速、不可达（pinned 334.8、pageable 383）。
   **E3-N pin 客户端 buffer 池（2 GiB）后 copy 411/415→336 µs**：b 1/1 **567.9 µs**、
   16/16 **9.990 GiB/s**；d 对照 1/1 **681.3 µs**、16/16 **11.380 GiB/s**（PCIe pinned
   聚合上限的 97%）。b 现在只剩 UB 栈 ~94 µs，硬件地板 ≈475 µs；
   **再往 475 推要动 UB 栈（E3-W），不是调参**。
7. **E3-V/E3-W/E3-X 把 UB 180 拆完**：E3-V total 180.7 = submit 27.0 + wait 153.0；
   E3-W 片数 63.9→1，total 只 180.3→157.0（−12.9%），**wait 恒 153.0–153.5**；
   切片只占 ~23，固定 ~71 与片数无关。E3-X 关掉 `MC_STORE_UB_POLL_SLEEP_US`：
   wait 153→90.3、total 178.3→**94.7**，b 1/1 **483.8 µs**（离地板 475 仅 9 µs）；
   固定 ~67 就是“睡 50 µs 再查”的完成发现延迟。16/16 的 busy poll 代价待 E3-Y。
8. **E3-Y/Z/AA 把 slice 选到 1M**：4M 在 16/16 最快（4MB 11.41、8MB 11.43 GiB/s），
   但正好等于 URMA 上限；**1M 是 4MB 96.1% / 8MB 99.3%，3/3 轮稳定**，单 WR 降到 1/4；
   256K/512K 在 4MB 是边缘通过。下一步 E3-AB 补 1/1 的 1M/sleep 折中。

## 2. 怎么判断数据是否合理：理论值与四层校验

### 2.1 先回答：有没有一个“理论值”可以直接对比？

有，但要**按指标分别算**，不存在一个“理论时延”能套所有点：

| 指标 | 理论/上界 | 怎么用 |
| --- | --- | --- |
| 高并发吞吐（16/16） | PCIe 3.0 x16 HBM write 14.67 GiB/s；实测 12.69 = 86.5%；UB 传输 b 21.9 | 实测 12.69/12.68，已到 PCIe HBM write 上限 |
| 高并发时延（16/16） | Little's law：在飞字节 ÷ 吞吐 | 实测与理论误差 <0.25%；16/16 是排队时长 |
| 单请求时延（1/1） | 传输 + 拷贝下限（4MB pinned 335 µs） | 直写 a 400 µs、暂存 b 656 µs、SSD c/d 470/773 µs |
| 暂存路径吞吐 | 直写吞吐减去拷贝段；相对值 61%–82% | 与 4MB/8MB 的拷贝标定同量级 |
| 8MB b 16/16 | 资源容量：staging pool ≥ 在飞字节 | 1 GiB < 2 GiB → 失败；4 GiB → 通过 |
| 缩放（4→8MB） | L = L0 + S/B | 直写高并发吞吐不变、时延 ×2；暂存 ×1.8 |

所以判断数据合理性，不是“拿一个理论时延比一下”，而是**四层校验**：

1. **定义自洽**：keys/s × size = 吞吐；queries/s × batch = keys/s；分位数单调。
2. **守恒律**：高并发下 avg 时延 ≈ 在飞字节 ÷ 吞吐（Little's law）。
3. **外部链路/组件**：PCIe HBM write 上限、UB 传输、PCIe host→HBM 拷贝、H2D 拷贝标定、SSD 尾延迟。
4. **缩放与 A/B**：4MB→8MB、直写 vs 暂存、首轮 vs 本轮；方向与幅度是否符合预期。
5. **资源容量与稳定性**：staging pool、落点、canary、失败率、段增长。

### 2.2 第一层：定义自洽

对 32 个点逐行检查：

- `keys/s × 对象大小` 与吞吐列一致（误差 <0.1%）；
- `queries/s × batch` 与 keys/s 一致（误差 <0.1%）；
- `min ≤ P50 ≤ P90 ≤ P99 ≤ P99.9 ≤ P99.99 ≤ Pmax`；
- `avg` 落在 min 与 Pmax 之间。

结论：32/32 通过。E3-F 那行 b 16/16 的计数矛盾（keys/s 3597.54 × 8 MiB ≈ 27.8 GiB/s
vs 实测 9.29）是失败态残留，E3-G 修复后已自洽（1207.57 × 8 MiB = 9.43 GiB/s）。

### 2.3 第二层：Little's law

稳态下：`avg 时延 = 在飞字节 ÷ 吞吐`。在飞字节 = read 线程 × batch × 对象大小
（假设每个 read 线程的 batch 全部在飞）。

**16/16（4MB 在飞 1 GiB；8MB 在飞 2 GiB）**

| a | 78.80 / 78.757 | −0.05% | 157.60 / 157.420 | −0.11% |
| b | 116.01 / 115.918 | −0.08% | 212.09 / 211.648 | −0.21% |
| c | 78.86 / 78.824 | −0.05% | 157.73 / 157.609 | −0.08% |
| d | 106.38 / 106.311 | −0.06% | 192.86 / 192.642 | −0.11% |

**1/1（4MB 在飞 4 MiB；8MB 在飞 8 MiB）**

| 场景 | 4MB 理论 / 实测 (µs) | 误差 | 8MB 理论 / 实测 (µs) | 误差 |
| --- | --- | --- | --- | --- |
| a | 400.2 / 400.09 | −0.03% | 737.7 / 737.87 | +0.02% |
| b | 656.4 / 656.20 | −0.03% | 1051.5 / 1050.97 | −0.05% |

**1/16 与 16/1（在飞 64 MiB / 128 MiB）** 同样全部 <0.25%，示例：

- 4MB 16/1：a 4.925/4.92485 ms；b 6.861/6.857；c 4.937/4.9355；d 6.906/6.9069；
- 8MB 1/16：a 10.105/10.104 ms；b 13.572/13.576；c 10.280/10.273；d 15.225/15.225。

结论：时延、吞吐、并发数三者的关系完全一致；这验证了“在飞字节”模型、
单位换算和 bench 的 avg 口径。注意：这一层是**内部自洽**，还需要外部上界。

### 2.4 第三层：链路上限（E3-J 修正）

E3-J 实测（只读）：

| 设备 | BDF / 路径 | 链路 | 线速 |
| --- | --- | --- | --- |
| GPU V100 | `0000:27:00.0` | PCIe 3.0 x16（LnkCap/LnkSta 8 GT/s x16） | 15.75 GB/s |
| Mellanox CX-6 Dx | `0000:a6:00.0` | PCIe 4.0 x8（16 GT/s x8，主板仅布 8 lane） | 15.75 GB/s |
| **UB `udmac0d1e2`** | `/sys/devices/ub_bus_controller0/...`，驱动 `ubase` | **UB 总线，不走 PCIe**；port0 active_speed=12 / width=4 | 以实测 **46.4–46.9 GiB/s** 为准（E3-K） |

- Mooncake 的数据通路是 `--protocol=ub --device_name=udmac0d1e2`，走 **UB**；
  Mellanox 不是这条数据通路。
- **E3-I 修正**：a/c 直写的 12.69/12.68 GiB/s 是 **PCIe 3.0 x16 HBM write** 的 86.5%；
  UB 是传输通道，b 的 UB 读 178 µs ≈ 21.9 GiB/s，UB 不是 a/c 的瓶颈。
  E3-J 的“UB 12.69”是过度归因。
- host→HBM 拷贝走 V100 的 PCIe 3.0 x16，4 MiB 下限 266 µs（pinned 335 µs）；
  E3-I 实测 staging 拷贝 416 µs（pageable 384 + 32）。
- 用户提供 UB 单向峰值 **46.4–46.9 GiB/s**（E3-K 实测；约 47）；
  E3-I 的 b UB 读 178 µs = 4 MiB/178µs ≈ **21.9 GiB/s**（4MB 单请求），
  是峰值的 47%，单请求未打满，不矛盾。**1/1 单请求不是上限；比带宽用 16/16**。
  E3-L2：1→16 在飞，UB 段恒为 180–181 µs（不降），copy 414→6589 µs 才是瓶颈（§3.7）。
  a/c 直写 12.69 只用 UB 峰值 27%；UB 不是 a/c 的瓶颈；a/c 的 12.69 = PCIe HBM write；
  b/d 的 copy 416 是主成本。
- urma_perf 26.4 GiB/s 是旧参照，不采用；UB 单向峰值以 **46.4–46.9 GiB/s** 为准（E3-K）。

### 2.5 第四层：组件下限与缩放

**拷贝标定（4MB H2D，300 次）**：pinned 335 µs（11.65 GiB/s）、
pageable 384 µs、2GB 4K 页 @NUMA0 411.5 µs、@NUMA2 501.2 µs。

单请求（1/1）实测与拷贝下限对比：

| 场景 | 4MB avg | 8MB avg | 解读 |
| --- | --- | --- | --- |
| a 直写 + 内存源 | 400.1 µs | 737.9 µs | 接近“传输 + 一次写入”，高于 335 µs 拷贝下限 |
| b 暂存 + 内存源 | 656.2 µs | 1051.0 µs | 比 a 多 256/313 µs；E3-L2 拆出 UB 180 + copy 414，净增量来自 copy 414 与 a 的 HBM write 355 之差；pageable 纯拷贝实测 414，不是 266 |
| c 直写 + SSD 源 | 469.6 µs | 759.7 µs | 比 a 多约 70 µs，SSD/NoF 侧增量 |
| d 暂存 + SSD 源 | 772.9 µs | 1243.7 µs | 比 c 多 303/484 µs，暂存拷贝增量 |

注意：b−a、d−c 不等于一次纯拷贝时间（两条路径的固定开销不同，不能简单相加）；
E3-L2 直接测得 b 的 UB 180 + copy 414，b−a 259 的净增量成立（见 §3.7）。

**4MB→8MB 缩放**：用 `L = L0 + S/B` 描述。

| 场景 | 1/1 时延比 | 16/1 | 1/16 | 16/16 | 高并发吞吐变化 |
| --- | --- | --- | --- | --- | --- |
| a | 1.84 | 2.00 | 1.96 | 2.00 | 0% |

- 直写高并发时延 ×2.00、吞吐不变：2 GiB 在飞、同一带宽，符合 Little's law；
- 暂存 ×1.8：8MB 下吞吐更高（大对象摊薄固定开销），所以时延不到 2×；
- 1/1 时直写 a 的 1.84（固定开销小，接近 2×），暂存 b/c/d 的 1.6（固定开销大）。

### 2.6 第五层：资源容量（8MB b 16/16）

- 8MB × 16 × 16 = **2 GiB 在飞**；
- UB transport staging pool 默认 **1 GiB**（`kDefaultUbStagingPoolSize = 1<<30`）；
- 1 GiB < 2 GiB → `acquireStaging` 返回 pool exhausted → client 层 `TRANSFER_FAIL`；
- 4MB × 16 × 16 = 1 GiB，刚好卡在默认池边界，所以 4MB 成功、8MB 失败；
- A/B：1G → failed 139678（91%）；4 GiB（4294967296）→ failed=0；8 GiB → failed=0；4 GiB 是最小可用值。

这是“容量约束”，不是性能异常；修复后 Little's law 仍成立（2 GiB ÷ 9.43 = 212.1 ms，
实测 211.6 ms）。

**风险提示**：4MB b 16/16 在 1G 池边界，能过但没有余量；后续建议统一设 4 GiB（4294967296）。

| keys/s | 3597.54（不可信） | 1207.57 |

**不要把 211.6 ms 与失败态的 71 ms 对比**：71 ms 是少数成功请求的幸存者偏差；
211.6 ms 才是 16/16 过载点的真实排队时长。若看单请求能力，用 1/1 的 1051 µs。

### 3.5 4MB / 1/1 单请求时延拆解（旧模型，E3-I 后以 §3.6 为准）

> 本节 92 / 266 / 335 / 308 的模型已被 E3-I 直接打点替代；保留作为推导历史，**数据以 §3.6 为准**。

#### 3.5.0 先统一口径：数据通路是 UB，PCIe 只用于 host→HBM

E3-J 已确认：`--protocol=ub --device_name=udmac0d1e2` 走 **UB**（`udmac0d1e2` 不是 PCIe 设备）；
PCIe 3.0 x16 只出现在 **host→HBM 拷贝** 和 GPU 侧。

- a：UB → GPU HBM（UB 308 µs；进 GPU 过 PCIe 3.0 x16，但 UB 是瓶颈）。
- b：UB → host DRAM（UB 308），host DRAM → HBM（PCIe 3.0 x16，266–335）。
- c：UB → GPU HBM（UB 308）+ SSD/NoF 70。
- d：UB → host DRAM（UB 308）+ host → HBM（PCIe 266–335）+ SSD/NoF 70。
- **UB 4 MiB 的实测下限**：`4 MiB / 12.69 GiB/s = 307.8 µs`（a 的数据面）。
- **PCIe 4 MiB 过一次 3.0 x16 的下限**：`266.2 µs`（只适用于 host→HBM 拷贝；pinned 335）。
- 所以 b/d 的第一次 crossing 是 **UB**，不是 PCIe；266 只适用于 b/d 的第二次 crossing。

#### 3.5.1 四个实测值

| 场景 | 4MB 1/1 avg |

| b | 656.20 µs |

#### 3.5.2 a 的拆解：组长判断正确

- 数据面：4 MiB ÷ 12.69 GiB/s = **307.8 µs**（UB 链路；E3-J 确认 UB 不走 PCIe）。
- 控制面/其他：400.1 − 307.8 = **92.3 µs**，含 query/RPC、元数据、replica 选择、
  buffer 分配、提交/完成、释放。
- 组长说的“数据面 300+、RPC 几十”结构正确；但 300+ 是 **UB**，不是 PCIe。
- 关于 12.75：15.75 GB/s × 87% = 13.70 GB/s = 12.76 GiB/s，这是 **PCIe 3.0 x16 的 87% 比值**；
  **实测 12.69 是 UB 上限，不是 PCIe 利用率**（E3-J）。12.75 只是巧合的比值，
  不要把 12.75 当 12.69 的理论值；UB 不在 PCIe 上。

#### 3.5.3 b 的 656：256.1 是净增量，不是纯拷贝

- `b − a = 256.1 µs` 是**净增量**，不是纯拷贝时间。这个质疑成立。
- b 的第一次 crossing（UB→host）与 a 的第一次 crossing（UB→HBM）都是 **UB 308 µs**；
  b 多的是一次 **PCIe host→HBM 拷贝**：4 MiB 过 3.0 x16 的下限 266.2 µs，pinned 335.3。
- 实测拷贝标定：pinned 335.3 µs（η=79%）、pageable 384.0（69%）、
  4K@NUMA0 411.5（65%）、4K@NUMA2 501.2（53%）。
- b 的理论下限：`UB 308 + PCIe 266 + control 92 = 666 µs`；实测 656，低 10 µs（1.5%），
  已经是 UB+PCIe 的物理地板。
- `b − a = 256.1 < 266.2`：说明 b 的第一次 UB / 控制比 a 快 ~10 µs（或测量误差）；
  **纯 PCIe 拷贝必然 ≥266 µs，不能把 256.1 当纯拷贝**。
- 组长的 500+ = `UB 308 + 拷贝 100 + control 92`；100 µs 的 4 MiB PCIe 拷贝 = 42 GB/s，
  超过 15.75 GB/s，物理上做不到；1/1 也没有重叠。
- 结论：**656 不是异常；500+ 低于物理下限 666**（E3-J 已确认 UB，不是 PCIe 4.0/5.0）。

- 当前 b 的 256.1 是 b−a 的净差，不能单独归因；建议在 b 路径加 PerfPoint/时间戳：

### 3.6 E3-I 打点实测（4MB / 1/1，替代 §3.5 的模型）

#### 3.6.1 打点方法与批次

#### 3.6.3 对 §3.5 的修正

1. **control 92 µs 不成立**：实测 query 35–42 + residual 5–12 = **41–54 µs**；
   92 是 a 400 − 308 的残差，不是控制面。
2. **copy 416 µs，不是 266/335**：staging 池是 `numa_alloc_onnode`/mmap 的 **pageable**
   内存，未 pin；416 = pageable 384 + 32（SetContext 等固定开销）。pinned 335 不适用；
   266 只是 PCIe 线速下限，不是实际。
3. **b−a = 259 µs 的净增量成立**：copy 416 −（a H2D 355 − b UB 178 = 177）≈ 239；
   实测 259；b 多了 copy、少了 GPU 直写。
4. **UB 308 是模型，不是实测**：E3-I 显示 b UB 178、d NoF 337（R16 同埋点 225）；a H2D 355、c NoF 379。
5. **12.69 GiB/s 是 PCIe 3.0 x16 HBM write，不是 UB**：a/c 直写 12.69 = PCIe 86.5%；
   b 的 UB 178 µs = 4 MiB/178µs ≈ **21.9 GiB/s**，UB 比 PCIe HBM write 快，
   不是 a/c 的瓶颈。E3-J 的“UB 12.69”是过度归因；**数据通路是 UB，
   但 a/c 直写的瓶颈是 PCIe HBM write**；12.75/87% 是 PCIe 直写。

#### 3.6.4 b 的 650 与组长的 500+

- b 650 = UB 178 + copy 416 + query 42 + residual 12。
- 500+ 假设 copy ~266；实际 copy 416（pageable 384+32）；**只压 copy 最多到 569**。
- E3-L2 实测（§3.7）：1→2→4→16 在飞，UB 段 180/180/181/181，**不降**；
  copy 414/603/1460/6589；b 1/1 物理下限 = 180+414 = 594（不含控制），实测 648；
  pin 后 180+335=515，加控制约 557–569。
- **E3-U 更正（§3.8）**：裸 UB 单请求 86.4 µs；180 是 Mooncake UB 栈（+94）；
  pinned copy 334.8、pageable 383；硬件地板 86.4+334.8+54 ≈ **475**。
  只 pin ≈ 569、只 UB 栈 ≈ 554；**500+ 需双杠杆**。
  原“UB 178→~120→~90、b 1/4≈560”的预期被实测否掉。

#### 3.6.5 结论

- 4MB/1/1 直接实测：a 391 / b 650 / c 419 / d 808（E3-I）。d 的 808 是重尾补跑批次，
  R16 同埋点 avg 768；交付用 R08：400 / 656 / 470 / 773（avg；批次差 2–7%）。
- b 的 copy 416 是 staging 主成本；UB 178 很快；a/c 直写是 PCIe HBM write；
  b/d 是 UB 读 + PCIe copy。
- 12.69 = PCIe HBM write；UB 传输 21.9；a/c 的瓶颈是 PCIe HBM write，不是 UB。

### 3.7 E3-L2 实测：UB 段恒定，copy 是唯一瓶颈（4MB / b）

#### 3.7.1 方法

- 4MB b 场景，`--gpu_mode=staging`；1/2/4/16 个在飞请求用 batch=1 跑分段，
  另用 16 线程 × batch=16 单独跑 16/16 吞吐；每点 60 s。
- batch>1 会切到 `batch_get_into`，逐请求埋点不产生（§3.7.4），所以**分段只用 batch=1**，
  吞吐点用 batch=16；两类点不混。
- 回执未说明独占状态（E3-K 曾发现 node2/node4 有他人 perftest）；但 t16 b16 与 R08 的 b 16/16
  差 0.6%，条件可比。高精度复核仍需独占（用户已说明会申请）。

#### 3.7.2 结果

| 在飞请求 | UB 段 µs | copy 段 µs | total µs | 吞吐 GiB/s | copy 聚合 GiB/s |
| --- | --- | --- | --- | --- | --- |
| 1 | 180 | 414 | 648 | 6.09 | 9.44 |
| 2 | 180 | 603 | 853 | 9.14 | 12.96 |
| 4 | 181 | 1460 | 1712 | 9.13 | 10.70 |
| 16 | 181 | 6589 | 6837 | 9.14 | 9.49 |
| 16×16（256 在飞） | — | — | 115145 | 8.67（8.66/8.69/8.67） | — |

- 吞吐 = 在飞 × 4 MiB ÷ total；copy 聚合 = 在飞 × 4 MiB ÷ copy 段。
- 1/2/4/16 点各 1 轮（n=1），只作分段；16/16 为 3 轮，avg 115145 µs vs R08 115918 µs（−0.7%）。
- total 的构成：1/2/4/16 点分别是 `UB + copy + query/其他`；b 1/1 的 648 =
  180 + 414 + 42（query）+ 12（residual）。

#### 3.7.3 三条结论

1. **UB 段不随并发下降**：180/180/181/181。copy 才是瓶颈：16 在飞时
   UB 占空比 ≈ 16×181/6837 = 42%，NIC 不排队，所以每请求的 UB 服务时间不变。
   原预期“178→~120→~90”基于“UB 是瓶颈”的前提，**被实测否掉**；UB 不是可调项。
   E3-L2 的 180–181 与 E3-I 的 178 相差约 1–2%，同一量级（批次差）。
   （180 是“1 个 4 MiB 在飞”的服务时间；它是固定时延还是单流 21.9 GiB/s 的带宽限制，
   本实验不能区分；对 b 的结论无影响，因为 copy 414 更大。）
2. **copy 不随并发扩展**：414→603→1460→6589 µs；聚合 9.44/12.96/10.70/9.49 GiB/s，
   2 并发峰值 13.0，4/16 回落到 10.7/9.5。16/16 的 copy 聚合 9.49 GiB/s，
   整体吞吐 8.67（copy + UB/控制）；这条 copy 墙决定了 b 的上限。
   机制候选（未证）：staging 池是 `numa_alloc_local` 的 pageable 内存，
   `CopyFromHost` 是同步 `cudaMemcpy` H2D；pageable 路径每次要 pin/unpin，
   高并发下不扩展。源码：`UbTransport::acquireStaging` 用 `ub_allocate_memory`；
   全仓 `cudaHostRegister` 只用于 store segment，且 `IsHostStoreSegmentProtocol`
   明确排除 `ub`，所以该池当前未 pin。
3. **b 的 500+：现行实现 594 下限，硬件地板约 475**（E3-U）：
   - 现行实现：UB 180 + copy 414 = **594 µs**（不含控制）；实测 648。
   - 硬件地板：裸 UB 86.4 + pinned copy 334.8 = **421 µs**；加控制 54 ≈ **475 µs**。
   - 只 pin copy：180+335+54 ≈ **569**；只优化 UB 栈：86.4+414+54 ≈ **554**；
     两个都做：**475 µs**（若 Mooncake copy 的 31 µs 额外开销仍在，约 506）。
   - 所以 500+ 不是单旋钮能到：**必须同时压 UB 栈（−94）和 pageable copy（−79）**；
     266 µs 线速不可达，pinned 单 copy 334.8 是实测地板。详见 §3.8。

#### 3.7.4 两条复现坑（必须记录）

1. **batch>1 让逐请求埋点失效**：batch>1 走 `batch_get_into`，
   `get_into / transfer_data / scatter_copy` 计数为 0；分段必须用 batch=1。
   回执摘录：`b=1 7065 7065 140518；b=2 1 1 5；b=16 0 0 0`。
2. **`MC_UB_STAGING_POOL_SIZE` 只认纯数字字节**：`std::stoull("4G")` = 4，

   `registered CPU staging pool ... size=4194304`；必须写 `4294967296`。
   该失败不抛异常、静默降级；E3-G 的脚本用的是字节写法，本轮照抄简写才踩到。

#### 3.7.5 对交付与下一步的影响

### 3.8 E3-U 更正：UB 单请求 86.4 µs，PCIe 266 µs 不可达

### 3.9 E3-N 实测：pin 客户端 buffer 池，copy 411/415→336 µs（4MB）

#### 3.9.1 方法

- A 臂 b 1/1 660.2 µs vs R16 648 µs：node2 load 36–40（308 核），**只做同窗口 A/B 比较，

#### 3.9.2 结果

**pin 后的模型（4MB / 1/1）**

- b：568 = UB 180 + copy 336 + 控制 52；地板 475 = UB 86.4 + copy 334.8 + 控制 54；
  **剩余 93 µs 全在 UB 栈**，copy 已不再是第一瓶颈。
- d：681 比 b 高 113，差值在 NoF/SSD 段与控制/批次；相对 E3-U 地板 558 的 123 中，
  UB 栈 ~94 仍在，其余 ~29 为 NoF/控制。d 的 16/16 已证明高并发受 copy 墙限制，
  单请求仍有 NoF 栈空间。
- **b 568→475 仍要动 UB 栈**：copy 杠杆已经做掉；E3-V/E3-W 已证明切片只占 ~23，
  固定 wait ~67 是下一目标（E3-X，§3.11）。

#### 3.9.3 pin 位置更正与池身份（E3-V 已复核）

- 任务书原假设 pin `UbTransport::acquireStaging` 池。实测：**4MB b/d 1/1（batch=1）走的是
  store 层 `client_buffer_allocator_`（`--local_buffer_size=2G`），b/d 共用**；b 场景
  `registered CPU staging pool` 计数为 0，staging 模式下 UB transport 池未分配。
  pin 打在客户端 buffer 池，b/d 同时受益，与结果一致。
- **16/16（batch=16）两个池都在用**：4MB b 16/16 与 8MB b 16/16 的
  `registered CPU staging pool = 1`（2 GiB，`ub_transport.cpp:269`）且 client 池也 pin；
  因此 E3-N 的 16/16 收益含两个池，不能只记给 client 池；1/1 只含 client 池，无歧义。
- **8MB b 16/16 的池身份已确认**：E3-G 的 `MC_UB_STAGING_POOL_SIZE=4294967296`
  修复根因是 UB staging 池，方向正确；8MB 结论保留“设 4 GiB 后 9.43 GiB/s / 211.6 ms 有效”。
- `MC_STORE_PIN_MEMORY_MAX_BYTES` 只 pin 全局 segment（`TryPinStoreSegment`），
  与本轮客户端 buffer 池 pin 无关。

#### 3.9.4 证据与风险

- pin 证据：`cudaHostRegister rc=0`（2 GiB，96.63 ms）；拷贝微测 384.3→335.8 µs；
  `cudaPointerGetAttributes` 由 Other 变为 Host(pinned/registered)。
  `VmLck=0` 属预期：`pin_user_pages` 记入 `mm->pinned_vm`，不是 `locked_vm`；
  `ulimit -l` 64 MiB 不构成限制。
- 风险：`cudaHostUnregister` 只接在 UB staging 池的析构；**client buffer 池没有配对的
  unregister**，实验进程退出可接受，上生产需在 allocator 析构补；2 GiB 常驻 pin 的
  生产影响未评估；改动默认关闭，未提交上游。

#### 3.9.5 结论

1. **copy 杠杆坐实**：pin 客户端 buffer 池后 copy 411/415→336 µs，四个点全部上升；
   b +16.2%/+19.6%，d 对照 +13.5%/+25.1%。
2. **d 16/16 到 PCIe copy 墙**（96%–97%）；b 16/16 仍受 UB 栈限制。
3. **b 剩余空间只有 UB 栈**：568 离地板 475 的 93 µs 全是 UB 180−86.4；
   E3-V 已把 180 拆成 submit 27.0 + wait 153.0；E3-W 证明切片只占 ~23，
   固定 wait ~67 是下一目标（E3-X，§3.11）。

### 3.10 E3-V 实测：UB 180 µs 的构成（4MB b 1/1，pin）

#### 3.10.1 方法

- 4MB b 1/1，`MC_UB_STAGING_POOL_PIN=1`；`MC_UB_WORKER_DIAG=1`、
  `MC_HIFREQ_LOG_SAMPLE_RATE=1`。
- diag 开销对照（同窗口 10 s）：6.77 → 6.80 GiB/s（−0.40% / +0.38%），<3% 合格。
- 正式 3 轮 60 s：6.85 / 6.84 / 6.83 GiB/s；avg 569.75 / 571.14 / 571.88 µs；failed=0。
- batch=1 不走 `batch_get_data_breakdown`（0 行），client 侧用 `transfer_data_breakdown`
  的 `submit_us / wait_us / total_us`；worker 侧取稳态区间、按 `completed_slices` 加权。

#### 3.10.2 结果

| 层 | µs | 占 180.7 |
| --- | --- | --- |
| client submit | 27.0 | 14.9% |
| worker queue_wait | 19.9（max 101） | 11.0% |
| worker post_call | 11.2 | 6.2% |
| post→CQ | 56.4（max 158） | 31.2% |
| 未归因残差 | 66.2 | 36.7% |
| **合计** | **180.7** | **100%** |

- client total 180.7 与 E3-N 的 180 吻合；get_into：query 38.3 / read 525.3 / total 565.3，
  read ≈ UB 180.7 + copy 336。
- worker 侧 `poll_call 0.10 µs/call`（≈43 万次/s，≈4% 单核），`dequeue 0.17/slice`，
  `active_loop_gap_max 36`，`63.9 片/请求（64 KiB/片；R20 原 31.9 是算错，见 §3.11.1）`。

#### 3.10.3 怎么读

- **第一可归因大头是 `post→CQ 56.4 µs/片`（31.2%）**，属于 URMA 完成/链路 + 软件轮询检测；
  不是软件 post 路径（11.2），也不是 worker 唤醒（19.9）。`poll_call` 只有 0.1 µs/call，
  排除轮询空转。
- **残差 66.2 不是漏埋点**：4 MiB 被切成 63.9×64 KiB 并发 post，worker 指标是单切片口径，
  不能对请求级总量直接求和；请求级 `wait 153 ≈ 首片延迟 + 64 片流水尾巴`。
  `post_to_cq 56.4` 是 64 片流水下的单切片均值，不能和 E3-U 的裸 86.4（整请求）直接比。
- **E3-W 更正**：wait 在 64→1 片恒为 153.0–153.5 µs；切片流水只解释 ~23 µs（全在 submit），
  剩余 ~67 µs 与片数无关。所以残差不是“切片尾巴”，而是一个固定 wait 成分（§3.11）。

#### 3.10.4 下一步

- E3-W 已完成：切片调大只能拿回 ~23 µs，1 片 total 仍 157 µs；固定 ~67 µs 是下一目标。
  见 §3.11。

## 4. 逐场景分析

### a：GDR 直写 + 内存源

## 5. 数据质量与异常

1. **node2 load 尖峰**：20:14 的 5 分钟 load 53.23，之后单调回落；4MB a 组前 9 点
   在衰减期采集。40 点内部极差多数 <1%，canary 漂移 <0.65%，判为未影响；
   若要绝对干净，低负载窗口复测 a 组。
2. **轮次**：1/16 与 16/16 各 2 轮，中位数意义弱于 3 轮的 1/1 与 16/1；
   但两轮差异很小（多数 <1%）。
3. **NoF 掉链**：4MB 1/41（2.4%），seq=31 d 1/1 r1 重跑成功；8MB 0 次。
4. **b 路径计数器**：a/b 的 `cuda_io`/`host_io` 均为 0，无法用计数器证明路径；
   既有埋点缺口。8MB b 16/16 的 staging pool 溢出/修复是行为级证据。
5. **8MB verify**：`--key_include_value_size=true` 与 `--verify=true` 互斥
   （KeySeed 不认 `_vs<bytes>` 后缀）；完整性用"写 100/100 + 四路径抽 key + 全量回读"三证。
6. **16/16 时延是排队时长**：a 78.8/157.4 ms、b 115.9/211.6 ms、c 78.8/157.6 ms、
   d 106.3/192.6 ms；不要当作单请求服务时间，也不要在 4MB/8MB 之间当作能力对比。
7. **4MB b 16/16 在 staging pool 边界**：1 GiB 在飞 = 默认 1 GiB 池；能过但无余量。
8. **残留 4 GiB 段**：`141.61.84.151:50411` 仍在（历史遗留），不影响 c/d；
   a/b 自动发现未受影响（本轮 a/b 均成功）。
9. **4MB R08 vs 首轮**：本轮 b/d 因绑核/GDR 明显变快，a/c 高并发不变；
   归因未拆（GDR + 2G 池 + gseg0 + 绑 N0 四项同时变）。方向与幅度合理。
10. **node2/node4 不再独占（E3-K）**：15:54–15:56 发现他人 root 的
    `urma_perftest send_lat` / `Round 8 remote worker`（来自 node1）；
    共享 UB 端口，write_bw 从 46 掉到 15–30 GiB/s；用户会协调独占；
    高精度测试前确认占用；R08/R09 的 a 组 / 8MB b 16/16 在独占后复核。
11. **E3-L2 的复现坑与批次条件**：batch>1 时逐请求埋点为 0（走 `batch_get_into`），
    分段只能用 batch=1；`MC_UB_STAGING_POOL_SIZE` 只认字节，`4G` 会解析成 4（4 MiB 池），
    导致 94% `Memory` 失败且静默降级，必须写 `4294967296`。E3-L2 未声明独占，
    t16 b16 与 R08 差 0.6%，暂按可比；独占后仍建议复核 b 16/16 与 a 组。

## 6. 结论

1. **数据合理**：通过定义自洽、Little's law、PCIe HBM write 上限、PCIe 拷贝下限、缩放模型、
   资源容量、稳定性七类检查；32/32 有效点，无自相矛盾。
2. **直写路径是 PCIe 3.0 x16 HBM write 受限**：12.69/12.68 GiB/s = PCIe 的 86.5%；
   UB 是传输，b 的 UB 读 178 µs ≈ 21.9 GiB/s（E3-I）；4MB/8MB、1/16/16/1 多点一致。
3. **暂存路径的差值是真实的 host 拷贝开销**：b/d 为直写的 61%–82%，
   8MB 下因摊薄固定开销而提升；b/d 的 16/16 差距（b 9.43 vs d 10.37）
   说明 NoF 暂存实现更优，可作为后续优化点。
4. **8MB b 16/16 是容量问题，不是性能问题**：1G 池 < 2G 在飞；4 GiB 修复后
   9.43 GiB/s / 211.6 ms，Little's law 吻合。
5. **尾延迟在存储侧**：SSD 源 Pmax 3.1–3.4 ms，远高于内存源 0.8–1.3 ms；
   直写消不掉 SSD 尾部。
6. **数据可用于交付**：最终两表 16/16 格有效；只需在交付说明中注明
   16/16 排队口径、b 计数器缺口、8MB verify 限制、4MB b 16/16 池边界。
7. **b 的优化空间已定量并验证一半（E3-U / E3-N）**：裸 UB 单请求 86.4 µs（45.1 GiB/s）；
   Mooncake 180 是栈 +94；PCIe 266 不可达，pinned copy 334.8 / pageable 383。
   **E3-N pin 客户端 buffer 池后 copy 411/415→336 µs：b 1/1 568、16/16 9.99；
   d 1/1 681、16/16 11.38（PCIe pinned 上限的 96%–97%）**。b 现在 568，地板 475，
   剩余 93 µs 全在 UB 栈。
8. **UB 栈已拆完（E3-V / E3-W / E3-X）**：E3-V total 180.7 = submit 27.0 + wait 153.0；
   E3-W 片数 63.9→1，total 180.3→157.0（−12.9%），wait 恒 153.0–153.5，
   切片只占 ~23；E3-X 关 `MC_STORE_UB_POLL_SLEEP_US` 后 wait 153→90.3、
   total 178.3→94.7，b 1/1 **483.8 µs**；固定 ~67 是完成发现延迟，
   UB 剩余只有 ~4 µs。
9. **E3-Y：16/16 的 busy poll 零收益，4M slice 是主收益**：16/16 下 sleep 0/10/50
   吞吐都是 11.41/11.40/11.41 GiB/s，CPU 6.5→16.8 核（2.6×）；4M vs 64K 是
   **11.41 vs 9.86（+15.7%）**，11.41 = PCIe pinned 上限的 **96.4%**。
   **16/16 保留默认 sleep=50，busy poll 只用于 1/1**；4M slice 在 1/1/16/16 都有效。
10. **E3-Z：4M 可外推到 8MB b，d 不受 slice 影响**：8MB b 4M 11.43 vs 64K 10.20
    （+12.1%），11.43 = PCIe 的 **96.5%**；d 4M/64K 都是 11.39，但 NoF 路径不消费
    `MC_SLICE_SIZE`，两臂是同一配置，不能当收益。4M 正好等于
    `SPDK_URMA_MAX_IO_SIZE`，单 WR 风险最大；1/1 六档里 256K→4M 只差 6 µs，
    **4M 在 1/1 不是必需**。E3-AA 已补中间档，见 11。
11. **E3-AA：共用配置选 1M**：4MB 256K/512K 是边缘通过（各 2/3 轮过阈），
    1M 三轮 11.08/10.97/10.95 = **96.1%**；8MB 512K 99.0%、1M 99.3%（3/3 轮）。
    1M 把单 WR 从 4M（URMA 上限）降到 1/4，代价 4MB −3.9%、8MB −0.7%；
    **256K/512K 不建议生产默认**。
12. **E3-AB：1M 在 1/1 等价 4M**：4MB avg 483.29 vs 483.77（−0.1%）、8MB −0.2%；
    wait 对 sleep 是斜率≈1 的直线（91/113/123/153），sleep0 只剩 ~5 µs 非 URMA 开销。
    1/1 avg 随 sleep 0/10/20/50 = 483/511/522/551；16/16 的 1M CPU 仍缺，
    E3-AC 补 sleep0/10 后定“按并发配置”还是“单配置 sleep10”。
13. **E3-AC：16/16 保留默认 sleep，最终方案 A**：1M 下 16/16 三档吞吐 10.94–10.97 /
    11.36–11.37，sleep0 +9.71 核、sleep10 +1.82 核；**16/16 用默认 sleep=50**。
    最终：1/1 sleep=0（483.3），16/16 sleep=50（1M：4MB 10.97、8MB 11.37，CPU 9.18）；
    单配置 sleep10 不成立。
14. **E3-AD：方案 A 四场景零回退**：a 1/1 400→369（+8.5%）、b 656→484（+35.5%）、
    c 468 基本不动（+0.4%）、d 773→694（+11.5%）；16/16 a/c 保持 12.69/12.68，
    b 10.97（+26.8%），d 11.39（+21.2%）。c 1/1 不动反证收益来自 UB 等待。
    **a−b / c−d 是直写相对暂存的路径收益，不是 b/d 的优化项**；1/16、16/1 仍缺，
    E3-AE 补齐后再定稿生产配置。

## 7. 交付建议

1. 使用最终两表：`4MB-...xlsx`（R08）、`8MB-...xlsx`（R09）；回读均 OK=16。
2. 对外说明 16/16 时延是**排队时长**；单请求能力看 1/1（4MB a 400 µs、b 656 µs、
   c 470 µs、d 773 µs；8MB a 738 µs、b 1051 µs、c 760 µs、d 1244 µs）。
3. 8MB 复现必须带 `MC_UB_STAGING_POOL_SIZE=4294967296`（只认字节；写 `4G` 会变成 4 MiB 池）；
   4MB b 16/16 在 1G 边界，建议后续也设 4 GiB。
4. 8MB 必须带 `--key_include_value_size=true`，且不要与 `--verify=true` 同用；
   完整性用三证。
5. b 的路径计数器为 0，路径证明靠 flag + 延迟量级；建议后续补 b 的 buffer_domain 埋点。
6. 可选：4MB a 组在低负载窗口复测；1/16 与 16/16 补到 3 轮。
7. b 的优化：copy 杠杆已做（E3-N：pin 客户端 buffer 池，copy 411/415→336 µs；
   b 1/1 568、16/16 9.99；d 1/1 681、16/16 11.38）；UB 已由 E3-V/W/X/Y/Z/AA/AB/AC/AD 拆完：
   **方案 A 四场景零回退：1/1 sleep0（a 369、b 484、c 468、d 694）、
   16/16 sleep50（a 12.69、b 10.97、c 12.68、d 11.39）**；a−b / c−d 是直写收益，
   不是 b/d 的优化项。下一步 E3-AE 补 1/16、16/1；不要靠加并发或调 stripe/chunk。
8. 对外不要用 Mooncake 1/1 的 UB 21.9 去比裸 UB 45.1/峰值 46.9；裸 UB 单请求 86.4 µs，
   21.9 是 Mooncake 栈；比带宽用 16/16。
9. NoF 阵列 strip 保持 **64KB**；256KB + 128KB chunk 实测 c 1/1 −6.5%、d −2.5%、16/16 持平，已回滚；客户端 chunk 128KB。
