## 0. 结论摘要

1. **数据整体合理、内部自洽**：32 个有效点（4MB 16 + 8MB 16）全部满足
   keys/s × 对象大小 = 吞吐、queries/s × batch = keys/s、Little's law 误差 < 0.25%。
2. **直写路径已到 PCIe 3.0 x16 HBM write 上界**：a/c 在 16/16 达到 12.69 / 12.68 GiB/s，
   即 PCIe 3.0 x16 的 **86.5%**；UB 只是传输通道，b 的 UB 读 178 µs ≈ 21.9 GiB/s，
   UB 不是 a/c 的瓶颈（E3-I）。
3. **暂存路径的差值就是 host 暂存 + memcpy**：b/d 吞吐为直写的 61%–82%，
   8MB 下因大对象摊薄固定开销而提升（b 8.62→9.43，d 9.40→10.37 GiB/s）。
4. **8MB b 16/16 的唯一异常已定位并修复**：UB transport staging pool 默认 1 GiB，
   小于 2 GiB 在飞；设 4G 后 9.43 GiB/s / 211.6 ms，A/B 对照确认。
5. **最终两表 16/16 格全部有效**。剩余风险（node2 load 尖峰、1/16 与 16/16 仅 2 轮、
   b 路径计数器为 0、8MB verify 互斥）已在交付说明中注明，不改变结论。

## 2. 怎么判断数据是否合理：理论值与四层校验

### 2.1 先回答：有没有一个“理论值”可以直接对比？

有，但要**按指标分别算**，不存在一个“理论时延”能套所有点：

| 指标 | 理论/上界 | 怎么用 |
| --- | --- | --- |
| 高并发吞吐（16/16） | PCIe 3.0 x16 HBM write 14.67 GiB/s；实测 12.69 = 86.5%；UB 传输 b 21.9 | 实测 12.69/12.68，已到 PCIe HBM write 上限 |
| 高并发时延（16/16） | Little's law：在飞字节 ÷ 吞吐 | 实测与理论误差 <0.25%；16/16 是排队时长 |
| 单请求时延（1/1） | 传输 + 拷贝下限（4MB pinned 335 µs） | 直写 a 400 µs、暂存 b 656 µs、SSD c/d 470/773 µs |
| 暂存路径吞吐 | 直写吞吐减去拷贝段；相对值 61%–82% | 与 4MB/8MB 的拷贝标定同量级 |
| 8MB b 16/16 | 资源容量：staging pool ≥ 在飞字节 | 1 GiB < 2 GiB → 失败；4G → 通过 |
| 缩放（4→8MB） | L = L0 + S/B | 直写高并发吞吐不变、时延 ×2；暂存 ×1.8 |

所以判断数据合理性，不是“拿一个理论时延比一下”，而是**四层校验**：

1. **定义自洽**：keys/s × size = 吞吐；queries/s × batch = keys/s；分位数单调。
2. **守恒律**：高并发下 avg 时延 ≈ 在飞字节 ÷ 吞吐（Little's law）。
3. **外部链路/组件**：PCIe HBM write 上限、UB 传输、PCIe host→HBM 拷贝、H2D 拷贝标定、SSD 尾延迟。
4. **缩放与 A/B**：4MB→8MB、直写 vs 暂存、首轮 vs 本轮；方向与幅度是否符合预期。
5. **资源容量与稳定性**：staging pool、落点、canary、失败率、段增长。

### 2.2 第一层：定义自洽

对 32 个点逐行检查：

- `keys/s × 对象大小` 与吞吐列一致（误差 <0.1%）；
- `queries/s × batch` 与 keys/s 一致（误差 <0.1%）；
- `min ≤ P50 ≤ P90 ≤ P99 ≤ P99.9 ≤ P99.99 ≤ Pmax`；
- `avg` 落在 min 与 Pmax 之间。

结论：32/32 通过。E3-F 那行 b 16/16 的计数矛盾（keys/s 3597.54 × 8 MiB ≈ 27.8 GiB/s
vs 实测 9.29）是失败态残留，E3-G 修复后已自洽（1207.57 × 8 MiB = 9.43 GiB/s）。

### 2.3 第二层：Little's law

稳态下：`avg 时延 = 在飞字节 ÷ 吞吐`。在飞字节 = read 线程 × batch × 对象大小
（假设每个 read 线程的 batch 全部在飞）。

**16/16（4MB 在飞 1 GiB；8MB 在飞 2 GiB）**

| a | 78.80 / 78.757 | −0.05% | 157.60 / 157.420 | −0.11% |
| b | 116.01 / 115.918 | −0.08% | 212.09 / 211.648 | −0.21% |
| c | 78.86 / 78.824 | −0.05% | 157.73 / 157.609 | −0.08% |
| d | 106.38 / 106.311 | −0.06% | 192.86 / 192.642 | −0.11% |

**1/1（4MB 在飞 4 MiB；8MB 在飞 8 MiB）**

| 场景 | 4MB 理论 / 实测 (µs) | 误差 | 8MB 理论 / 实测 (µs) | 误差 |
| --- | --- | --- | --- | --- |
| a | 400.2 / 400.09 | −0.03% | 737.7 / 737.87 | +0.02% |
| b | 656.4 / 656.20 | −0.03% | 1051.5 / 1050.97 | −0.05% |
| c | 469.5 / 469.58 | +0.02% | 760.0 / 759.70 | −0.04% |
| d | 773.6 / 772.86 | −0.10% | 1244.0 / 1243.68 | −0.03% |

**1/16 与 16/1（在飞 64 MiB / 128 MiB）** 同样全部 <0.25%，示例：

- 4MB 16/1：a 4.925/4.92485 ms；b 6.861/6.857；c 4.937/4.9355；d 6.906/6.9069；
- 8MB 1/16：a 10.105/10.104 ms；b 13.572/13.576；c 10.280/10.273；d 15.225/15.225。

结论：时延、吞吐、并发数三者的关系完全一致；这验证了“在飞字节”模型、
单位换算和 bench 的 avg 口径。注意：这一层是**内部自洽**，还需要外部上界。

### 2.4 第三层：链路上限（E3-J 修正）

E3-J 实测（只读）：

| 设备 | BDF / 路径 | 链路 | 线速 |
| --- | --- | --- | --- |
| GPU V100 | `0000:27:00.0` | PCIe 3.0 x16（LnkCap/LnkSta 8 GT/s x16） | 15.75 GB/s |
| Mellanox CX-6 Dx | `0000:a6:00.0` | PCIe 4.0 x8（16 GT/s x8，主板仅布 8 lane） | 15.75 GB/s |
| **UB `udmac0d1e2`** | `/sys/devices/ub_bus_controller0/...`，驱动 `ubase` | **UB 总线，不走 PCIe**；port0 active_speed=12 / width=4 | 以实测 **12.68 GiB/s** 为准 |

- Mooncake 的数据通路是 `--protocol=ub --device_name=udmac0d1e2`，走 **UB**；
  Mellanox 不是这条数据通路。
- **E3-I 修正**：a/c 直写的 12.69/12.68 GiB/s 是 **PCIe 3.0 x16 HBM write** 的 86.5%；
  UB 是传输通道，b 的 UB 读 178 µs ≈ 21.9 GiB/s，UB 不是 a/c 的瓶颈。
  E3-J 的“UB 12.69”是过度归因。
- host→HBM 拷贝走 V100 的 PCIe 3.0 x16，4 MiB 下限 266 µs（pinned 335 µs）；
  E3-I 实测 staging 拷贝 416 µs（pageable 384 + 32）。
- 用户提供 UB 单向峰值 **46.4–46.9 GiB/s**（E3-K 实测；约 47）；
  E3-I 的 b UB 读 178 µs = 4 MiB/178µs ≈ **21.9 GiB/s**（4MB 单请求），
  是峰值的 47%，单请求未打满，不矛盾。a/c 直写 12.69 只用 UB 峰值 27%；
  UB 不是 a/c 的瓶颈；a/c 的 12.69 = PCIe HBM write；b/d 的 copy 416 是主成本。
- urma_perf 26.4 GiB/s 是旧参照，不采用；UB 单向峰值以 **46.4–46.9 GiB/s** 为准（E3-K）。

### 2.5 第四层：组件下限与缩放

**拷贝标定（4MB H2D，300 次）**：pinned 335 µs（11.65 GiB/s）、
pageable 384 µs、2GB 4K 页 @NUMA0 411.5 µs、@NUMA2 501.2 µs。

单请求（1/1）实测与拷贝下限对比：

| 场景 | 4MB avg | 8MB avg | 解读 |
| --- | --- | --- | --- |
| a 直写 + 内存源 | 400.1 µs | 737.9 µs | 接近“传输 + 一次写入”，高于 335 µs 拷贝下限 |
| b 暂存 + 内存源 | 656.2 µs | 1051.0 µs | 比 a 多 256/313 µs，是**净增量**（含读路径差异），不等于纯拷贝；纯拷贝下限 266 µs（见 §3.5） |

**4MB→8MB 缩放**：用 `L = L0 + S/B` 描述。

| 场景 | 1/1 时延比 | 16/1 | 1/16 | 16/16 | 高并发吞吐变化 |

- 暂存 ×1.8：8MB 下吞吐更高（大对象摊薄固定开销），所以时延不到 2×；
- 1/1 时直写 a 的 1.84（固定开销小，接近 2×），暂存 b/c/d 的 1.6（固定开销大）。

### 2.6 第五层：资源容量（8MB b 16/16）

- 8MB × 16 × 16 = **2 GiB 在飞**；
- UB transport staging pool 默认 **1 GiB**（`kDefaultUbStagingPoolSize = 1<<30`）；
- 1 GiB < 2 GiB → `acquireStaging` 返回 pool exhausted → client 层 `TRANSFER_FAIL`；
- 4MB × 16 × 16 = 1 GiB，刚好卡在默认池边界，所以 4MB 成功、8MB 失败；
- A/B：1G → failed 139678（91%）；4G → failed=0；8G → failed=0；4G 是最小可用值。

这是“容量约束”，不是性能异常；修复后 Little's law 仍成立（2 GiB ÷ 9.43 = 212.1 ms，
实测 211.6 ms）。

**风险提示**：4MB b 16/16 在 1G 池边界，能过但没有余量；后续建议统一设 4G。

### 3.5 4MB / 1/1 单请求时延拆解（旧模型，E3-I 后以 §3.6 为准）

> 本节 92 / 266 / 335 / 308 的模型已被 E3-I 直接打点替代；保留作为推导历史，**数据以 §3.6 为准**。

#### 3.5.0 先统一口径：数据通路是 UB，PCIe 只用于 host→HBM

E3-J 已确认：`--protocol=ub --device_name=udmac0d1e2` 走 **UB**（`udmac0d1e2` 不是 PCIe 设备）；
PCIe 3.0 x16 只出现在 **host→HBM 拷贝** 和 GPU 侧。

- a：UB → GPU HBM（UB 308 µs；进 GPU 过 PCIe 3.0 x16，但 UB 是瓶颈）。
- b：UB → host DRAM（UB 308），host DRAM → HBM（PCIe 3.0 x16，266–335）。
- c：UB → GPU HBM（UB 308）+ SSD/NoF 70。
- d：UB → host DRAM（UB 308）+ host → HBM（PCIe 266–335）+ SSD/NoF 70。
- **UB 4 MiB 的实测下限**：`4 MiB / 12.69 GiB/s = 307.8 µs`（a 的数据面）。
- **PCIe 4 MiB 过一次 3.0 x16 的下限**：`266.2 µs`（只适用于 host→HBM 拷贝；pinned 335）。
- 所以 b/d 的第一次 crossing 是 **UB**，不是 PCIe；266 只适用于 b/d 的第二次 crossing。

#### 3.5.1 四个实测值

| --- | --- |
| a | 400.09 µs |
| b | 656.20 µs |
| c | 469.58 µs |

#### 3.5.2 a 的拆解：组长判断正确

- 数据面：4 MiB ÷ 12.69 GiB/s = **307.8 µs**（UB 链路；E3-J 确认 UB 不走 PCIe）。
- 控制面/其他：400.1 − 307.8 = **92.3 µs**，含 query/RPC、元数据、replica 选择、
  buffer 分配、提交/完成、释放。
- 组长说的“数据面 300+、RPC 几十”结构正确；但 300+ 是 **UB**，不是 PCIe。
- 关于 12.75：15.75 GB/s × 87% = 13.70 GB/s = 12.76 GiB/s，这是 **PCIe 3.0 x16 的 87% 比值**；
  **实测 12.69 是 UB 上限，不是 PCIe 利用率**（E3-J）。12.75 只是巧合的比值，
  不要把 12.75 当 12.69 的理论值；UB 不在 PCIe 上。

#### 3.5.3 b 的 656：256.1 是净增量，不是纯拷贝

- `b − a = 256.1 µs` 是**净增量**，不是纯拷贝时间。这个质疑成立。
- b 的第一次 crossing（UB→host）与 a 的第一次 crossing（UB→HBM）都是 **UB 308 µs**；
  b 多的是一次 **PCIe host→HBM 拷贝**：4 MiB 过 3.0 x16 的下限 266.2 µs，pinned 335.3。
- 实测拷贝标定：pinned 335.3 µs（η=79%）、pageable 384.0（69%）、
  4K@NUMA0 411.5（65%）、4K@NUMA2 501.2（53%）。
- b 的理论下限：`UB 308 + PCIe 266 + control 92 = 666 µs`；实测 656，低 10 µs（1.5%），
  已经是 UB+PCIe 的物理地板。
- `b − a = 256.1 < 266.2`：说明 b 的第一次 UB / 控制比 a 快 ~10 µs（或测量误差）；
  **纯 PCIe 拷贝必然 ≥266 µs，不能把 256.1 当纯拷贝**。
- 组长的 500+ = `UB 308 + 拷贝 100 + control 92`；100 µs 的 4 MiB PCIe 拷贝 = 42 GB/s，
  超过 15.75 GB/s，物理上做不到；1/1 也没有重叠。
- 结论：**656 不是异常；500+ 低于物理下限 666**（E3-J 已确认 UB，不是 PCIe 4.0/5.0）。

**理论 vs 实测对照（4MB 1/1）**

| 场景 | UB 数据面 | PCIe 拷贝 | SSD/NoF | 控制 | 理论 | 实测 |
| --- | --- | --- | --- | --- | --- | --- |
| a | 308 | 0 | 0 | 92 | 400 | 400.1 |
| b | 308 | 266（pinned 335） | 0 | 92 | 666（735） | 656.2 |
| c | 308 | 0 | 70 | 92 | 470 | 469.6 |
| d | 308 | 303（266 + NoF 37） | 70 | 92 | 773 | 772.9 |

- UB 数据面用 a 的 308（12.69 GiB/s）；PCIe 拷贝用 266（线速）/335（pinned）。
- a/c 与模型一致；b 在 666–735 之间、贴近 666；d 与 773 一致。
- b 的 656 比 666 低 10（1.5%）；500+ = 308 + 100 + 92 = 500，拷贝 100 < 266，物理不可能。
- d 的 303 = PCIe 266 + NoF 37；b/d 的第二次 crossing 同量级。

#### 3.5.4 c/d 交叉验证

- c = a + 69.5 µs（SSD/NoF 增量）。
- d = c + 303.3 µs（PCIe 拷贝 266 + NoF 37）。
- b 的净增量 256.1、d 的 303.3，都是“第二次 PCIe 拷贝”；b/d 一致。
- 如果 b 应该是 500+（净增量 100），d 应该 ~607；d 实测 773，矛盾。
  b 的 656 才是自洽的。

#### 3.5.5 打点拆分（组长方向，正确）

- 当前 b 的 256.1 是 b−a 的净差，不能单独归因；建议在 b 路径加 PerfPoint/时间戳：
  `query/select → read into host → scatter (memcpy) → free`；a/c/d 同口径。
- 目标：把 656 拆成 `read_host / copy / control` 三段，直接验证：
  - copy（PCIe host→HBM）是否 266–335 µs；
  - read_host（UB→host）是否 ~308 µs；
  - control 是否 ~92 µs。
- 实现：SpDiag::PerfPoint 或 steady_clock 时间戳；env 门控、可回退；
  b 路径当前没有埋点（NoF staging 块也没有），需要一次本地重编。
- 判据：1/1 ×3；copy 段应与 pinned 335 / pageable 384 同量级；
  若 copy < 266，说明计量口径有问题（把 read 的一部分算进 copy 或重叠）。

### 3.6 E3-I 打点实测（4MB / 1/1，替代 §3.5 的模型）

#### 3.6.1 打点方法与批次

- 在 a/b/c/d 的 1/1 路径加 PerfPoint/时间戳，四段：`query/select`、`read`（含 transfer）、
  `scatter-copy`、`free`。
- 样本：1.1–2.3 万 request，copy 22–28 万；sample 0.05；不是抽样估计。
- 批次：a/c 来自主矩阵；b/d 是 15:10–15:17 的补跑 3 轮（吞吐略低：b 6.08–6.11、
  d 4.74–5.02 GiB/s）。**交付值仍用 R08**；分段为直接实测；两者差 2–7%。

#### 3.6.2 四段实测（µs，中位）

| 场景 | query | select | read | 其中 transfer | copy | residual | total | R08 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| a GDR + 内存 | 35 | 0 | 355 | 350 | — | 5 | **391** | 400 |
| b staging + 内存 | 42 | 0 | 606 | 178 | **416** | 12 | **650** | 656 |
| c GDR + NoF | 37 | 0 | 379 | 373 | — | 6 | **419** | 470 |
| d staging + NoF | 42 | 0 | 762 | 337 | **415** | 10 | **808** | 773 |

- b 的 read 606 = UB 178 + copy 416 + residual 12；
  d 的 read 762 = UB 337 + copy 415 + residual 10。
- a/c 直写无 copy；b/d 的 copy 416/415（pageable 384 + 32）。
- 分布：a read 355（354–357）、b copy 416（413–420）、d copy 415（412–419）；
  c/d 的 P90 484/922，是 NoF 长尾。
- 恒等式：`residual = read − transfer − copy`，5–12 µs。

#### 3.6.3 对 §3.5 的修正

1. **control 92 µs 不成立**：实测 query 35–42 + residual 5–12 = **41–54 µs**；
   92 是 a 400 − 308 的残差，不是控制面。
2. **copy 416 µs，不是 266/335**：staging 池是 `numa_alloc_onnode`/mmap 的 **pageable**
   内存，未 pin；416 = pageable 384 + 32（SetContext 等固定开销）。pinned 335 不适用；
   266 只是 PCIe 线速下限，不是实际。
3. **b−a = 259 µs 的净增量成立**：copy 416 −（a H2D 355 − b UB 178 = 177）≈ 239；
   实测 259；b 多了 copy、少了 GPU 直写。
4. **UB 308 是模型，不是实测**：E3-I 显示 b UB 178、d UB 337；a H2D 355、c NoF 379。
5. **12.69 GiB/s 是 PCIe 3.0 x16 HBM write，不是 UB**：a/c 直写 12.69 = PCIe 86.5%；
   b 的 UB 178 µs = 4 MiB/178µs ≈ **21.9 GiB/s**，UB 比 PCIe HBM write 快，
   不是 a/c 的瓶颈。E3-J 的“UB 12.69”是过度归因；**数据通路是 UB，
   但 a/c 直写的瓶颈是 PCIe HBM write**；12.75/87% 是 PCIe 直写。

#### 3.6.4 b 的 650 与组长的 500+

- b 650 = UB 178 + copy 416 + query 42 + residual 12。
- 500+ 假设 copy ~266；实际 copy 416（pageable 384+32）；500+ 比实际 650 低 150，
  1/1 不可达。

#### 3.6.5 结论

- 4MB/1/1 直接实测：a 391 / b 650 / c 419 / d 808（E3-I）；
  交付 R08 为 400 / 656 / 470 / 773（avg；批次差 2–7%，以 R08 为准）。
- b 的 copy 416 是 staging 主成本；UB 178 很快；a/c 直写是 PCIe HBM write；
  b/d 是 UB 读 + PCIe copy。
- 12.69 = PCIe HBM write；UB 传输 21.9；a/c 的瓶颈是 PCIe HBM write，不是 UB。

#### 3.6.6 UB 带宽（E3-K 已核实）

- 实测（node4↔node2，4 MiB，`-Q1`）：write 47487.20 MiB/s = **46.37 GiB/s**；
  read 48039.15 MiB/s = **46.91 GiB/s**；64 KiB 48048.54 MiB/s = **46.92 GiB/s**；
  双向 79842.37 = 77.97 GiB/s；J=4 不比 J=1 高 → 单设备/单向峰值 **46.4–46.9 GiB/s**。
- 工具列头 “MB/sec” 数值上是 **MiB/s**（除数 1024²）；`urma_check.sh` 不做换算，
  `awk '{print $4}'` 原样打印；47 = 48048.54 的四舍五入，按 **GiB/s** 引用正确。
- **CQ moderation 坑**：4 MiB + 默认 moderation=100 → 4051.73 MiB/s（3.96 GiB/s，
  低估 11.7×）；`-Q1` → 47487.20；64 KiB + moderation=100 → 48048.54（小消息绕开）。
  **4 MiB 场景必须 `-Q1`。**
- 与 E3-I：b UB 178 µs = 4 MiB/178µs = **21.9 GiB/s**（不是 22.5），是 4 MiB `-Q1`
  峰值的 47%；单请求未打满，合理。
- **26.4 GiB/s 是旧参照，不是 UB 峰值**；以 **46.4–46.9 GiB/s** 为准。
- **节点占用风险**：E3-K 在 node2/node4 发现他人 root 的 `urma_perftest send_lat` /
  `Round 8 remote worker`；共享 UB 端口，write_bw 从 46 掉到 15–30 GiB/s；
  **node2 不再是我方独占**（与 10-26 用户声明不一致）。高精度带宽/时延测试前
  必须由用户确认占用，否则数字不可复现；R08/R09 的 a 组 / 8MB b 16/16 需按此复核。

## 4. 逐场景分析

### a：GDR 直写 + 内存源

- 4MB：1/1 9.76 GiB/s / 400 µs；16/16 12.69 / 78.8 ms。
- 8MB：1/1 10.59 / 738 µs；16/16 12.69 / 157.4 ms。
- 16/1 与 16/16 都到 12.69 GiB/s（PCIe HBM write 上限）；1/1 未到，受固定开销限制。
- 8MB/4MB 1/1 时延 1.84×（固定开销小，接近 2×）；高并发 2.00×（排队翻倍）。
- 结论：a 是高并发基准；12.69 GiB/s 就是本平台 **PCIe 3.0 x16 HBM write** 的直写上界。

### b：staging 暂存 + 内存源

- 4MB：1/1 5.95 / 656 µs；16/16 8.62 / 115.9 ms。
- 8MB：1/1 7.43 / 1051 µs；16/16 9.43 / 211.6 ms。
- 8MB 16/16 曾 91% 失败，根因是 UB staging pool 1G < 2G 在飞；4G 修复。
- 4MB 16/16 在 1G 池边界，能过但无余量；建议后续统一 4G。
- b 的路径计数器为 0（UB 内存路径无 buffer_domain 埋点）；路径证明靠
  `--gpu_mode=staging` + 延迟量级 + 8MB 池溢出/修复这一行为证据。

### c：GDR 直写 + SSD(NoF) 源

- 4MB：1/1 8.32 / 470 µs；16/16 12.68 / 78.8 ms。
- 8MB：1/1 10.28 / 760 µs；16/16 12.68 / 157.6 ms。
- 高并发与 a 一样顶到 UB 上界；1/1 比 a 多约 70 µs，是 SSD/NoF 侧增量。
- Pmax 3.1–3.4 ms，尾部由存储侧主导。

### d：staging 暂存 + SSD(NoF) 源

- 4MB：1/1 5.05 / 773 µs；16/16 9.40 / 106.3 ms。
- 8MB：1/1 6.28 / 1244 µs；16/16 10.37 / 192.6 ms。
- 16/16 比 b 快（4MB 9.40 vs 8.62；8MB 10.37 vs 9.43），说明 NoF 暂存实现
  在高并发下优于 UB 暂存；这也是后续优化的候选点。
- Pmax 2.7–3.4 ms，SSD 尾部仍在。

## 5. 数据质量与异常

1. **node2 load 尖峰**：20:14 的 5 分钟 load 53.23，之后单调回落；4MB a 组前 9 点
   在衰减期采集。40 点内部极差多数 <1%，canary 漂移 <0.65%，判为未影响；
   若要绝对干净，低负载窗口复测 a 组。
2. **轮次**：1/16 与 16/16 各 2 轮，中位数意义弱于 3 轮的 1/1 与 16/1；
   但两轮差异很小（多数 <1%）。
3. **NoF 掉链**：4MB 1/41（2.4%），seq=31 d 1/1 r1 重跑成功；8MB 0 次。
4. **b 路径计数器**：a/b 的 `cuda_io`/`host_io` 均为 0，无法用计数器证明路径；
   既有埋点缺口。8MB b 16/16 的 staging pool 溢出/修复是行为级证据。
5. **8MB verify**：`--key_include_value_size=true` 与 `--verify=true` 互斥
   （KeySeed 不认 `_vs<bytes>` 后缀）；完整性用"写 100/100 + 四路径抽 key + 全量回读"三证。
6. **16/16 时延是排队时长**：a 78.8/157.4 ms、b 115.9/211.6 ms、c 78.8/157.6 ms、
   d 106.3/192.6 ms；不要当作单请求服务时间，也不要在 4MB/8MB 之间当作能力对比。
7. **4MB b 16/16 在 staging pool 边界**：1 GiB 在飞 = 默认 1 GiB 池；能过但无余量。
8. **残留 4 GiB 段**：`141.61.84.151:50411` 仍在（历史遗留），不影响 c/d；
   a/b 自动发现未受影响（本轮 a/b 均成功）。
9. **4MB R08 vs 首轮**：本轮 b/d 因绑核/GDR 明显变快，a/c 高并发不变；
   归因未拆（GDR + 2G 池 + gseg0 + 绑 N0 四项同时变）。方向与幅度合理。
10. **node2/node4 不再独占（E3-K）**：15:54–15:56 发现他人 root 的
    `urma_perftest send_lat` / `Round 8 remote worker`（来自 node1）；
    共享 UB 端口，write_bw 从 46 掉到 15–30 GiB/s；高精度测试前必须由用户确认占用；
    R08/R09 的 a 组 / 8MB b 16/16 需按此复核。

## 6. 结论

1. **数据合理**：通过定义自洽、Little's law、PCIe HBM write 上限、PCIe 拷贝下限、缩放模型、
   资源容量、稳定性七类检查；32/32 有效点，无自相矛盾。
2. **直写路径是 PCIe 3.0 x16 HBM write 受限**：12.69/12.68 GiB/s = PCIe 的 86.5%；
   UB 是传输，b 的 UB 读 178 µs ≈ 21.9 GiB/s（E3-I）；4MB/8MB、1/16/16/1 多点一致。
3. **暂存路径的差值是真实的 host 拷贝开销**：b/d 为直写的 61%–82%，
   8MB 下因摊薄固定开销而提升；b/d 的 16/16 差距（b 9.43 vs d 10.37）
   说明 NoF 暂存实现更优，可作为后续优化点。
4. **8MB b 16/16 是容量问题，不是性能问题**：1G 池 < 2G 在飞；4G 修复后
   9.43 GiB/s / 211.6 ms，Little's law 吻合。
5. **尾延迟在存储侧**：SSD 源 Pmax 3.1–3.4 ms，远高于内存源 0.8–1.3 ms；
   直写消不掉 SSD 尾部。
6. **数据可用于交付**：最终两表 16/16 格有效；只需在交付说明中注明
   16/16 排队口径、b 计数器缺口、8MB verify 限制、4MB b 16/16 池边界。

## 7. 交付建议

1. 使用最终两表：`4MB-...xlsx`（R08）、`8MB-...xlsx`（R09）；回读均 OK=16。
2. 对外说明 16/16 时延是**排队时长**；单请求能力看 1/1（4MB a 400 µs、b 656 µs、
   c 470 µs、d 773 µs；8MB a 738 µs、b 1051 µs、c 760 µs、d 1244 µs）。
3. 8MB 复现必须带 `MC_UB_STAGING_POOL_SIZE=4G`；4MB b 16/16 在 1G 边界，
   建议后续也设 4G。
4. 8MB 必须带 `--key_include_value_size=true`，且不要与 `--verify=true` 同用；
   完整性用三证。
5. b 的路径计数器为 0，路径证明靠 flag + 延迟量级；建议后续补 b 的 buffer_domain 埋点。
6. 可选：4MB a 组在低负载窗口复测；1/16 与 16/16 补到 3 轮。
